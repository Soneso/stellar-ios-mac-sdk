# AGENTS.md

This file is for everyone who changes the iOS and macOS Stellar SDK, people and agents alike. It holds what the tree does not show: the commands, what "done" means, which files are generated, the conventions that differ from Swift defaults, and the limits of a change. When this file and a file it names disagree, the named file wins, and the pull request that changes the fact updates this file. Users of the SDK read `README.md` and `docs/`; agents that build on the SDK read the skill under `skills/`.

## Commands

Setup is described in `CONTRIBUTING.md`. The Swift tools version and the platform floors are in `Package.swift`; `README.md` states the Xcode requirement.

```sh
swift build
swift test --filter stellarsdkUnitTests
swift test --filter 'stellarsdkUnitTests.StrKeyUnitTests/testIsValid$'
swift test --filter stellarsdkIntegrationTests
```

- `swift build` takes about half a minute from a clean tree. The unit suite (about 9,900 tests) takes about 75 seconds with a warm build; the first `swift test` after a build compiles both test targets and takes longer. Five unit tests reach live Horizon (see the mock rule below); every other unit test runs offline.
- `--filter` is a regular expression. Anchor a method name with `$`, otherwise `testIsValid` also runs `testIsValidPreAuthTx` and `testIsValidSha256Hash`. The XCTest line `Executed N tests` is the result; the Swift Testing line `0 tests in 0 suites` after it is noise.
- The integration suite runs against live testnet and futurenet with Friendbot funding, is not part of CI, and runs long. Integration tests choose their network per class with `static let testOn`.
- CI runs the unit suite with `--enable-code-coverage` and exports `coverage/lcov.info` through `xcrun llvm-cov export`.
- There is no lint or format configuration in the repository. Compiler warnings do not fail CI.
- The API documentation builds with `jazzy` into the gitignored `api-docs/` and takes about 20 minutes; it is release work.

## Definition of done

Before reporting a change as done:

1. `swift build` and the unit suite pass.
2. Area gates. After a generator, override, or XDR definition change: `make xdr-generate` leaves a clean tree, `make xdr-generator-test` passes, and `bundle exec ruby test/validate_generated_types.rb` in `tools/xdr-generator/` passes. After a change that touches XDR-JSON names or either SEP-51 pin: `ruby tools/sep-51-oracle/name_map.rb --offline-check`, `ruby tools/sep-51-oracle/emitted_names.rb` and `python3 tools/sep-51-corpus/generate_corpus.py --validate-committed`. After a matrix generator change: `python3 -m unittest discover -s tools/matrix-generator/tests`. After a change to a public API that a documentation page uses: the page's test under `stellarsdk/stellarsdkIntegrationTests/docs/`, changed in the same pull request.
3. A test that would fail without the change exists. A bug fix starts with the failing test. A new test resource is declared in `Package.swift`, otherwise every build prints an "unhandled file" warning.
4. `CHANGELOG.md` has an entry under `[Unreleased]` in the Keep a Changelog section the change belongs to (Added, Changed, Deprecated, Removed, Fixed, Security), in present tense, one entry per user-visible change.
5. No generated file was edited by hand. The user documentation under `docs/` and the skill under `skills/` describe the released SDK; they change on the `release-docs` branch with the release. `docs/documentation-strategy.md` is a process document and changes in the pull request that changes a fact it states.

Every pull request runs `.github/workflows/tests.yml`: the unit suite with coverage on a macOS runner, the Codecov upload, and the `agents-md-paths` job. That job runs `.github/scripts/check_agents_md_paths.py`, which fails when a path this file names does not exist, so a change that moves a file also changes the line here. `.github/workflows/xdr-generator.yml` runs when its path filter matches. It runs the generator snapshot tests and regenerates the three generated trees on Linux, where the case-sensitive file system also catches stray files; any tracked or untracked difference fails it. It also runs the SEP-51 checks, which include that `docs/sep/sep-51.md` and the skill's SEP-51 page quote the pinned SEP-51 version. The branch rules require the Codecov project status; `codecov.yml` holds the targets and the ignore list.

## Generated code and data

Generated files are never edited by hand. Change the generator or its override files and regenerate.

- **XDR types.** The files in `stellarsdk/stellarsdk/responses/xdr/` whose header says they were generated by xdrgen, the emitted test trees `stellarsdk/stellarsdkUnitTests/sep/txrep/generated/` and `stellarsdk/stellarsdkUnitTests/sep/xdr_json/generated/`, and the generator snapshots under `tools/xdr-generator/test/snapshots/`. Hand-written and left alone by the generator: the eight files in `stellarsdk/stellarsdk/responses/xdr/` without the header (the transaction, envelope, and muxed account types); `SKIP_TYPES` in `tools/xdr-generator/generator/generator.rb` lists the skipped types. Also hand-written: everything under `stellarsdk/stellarsdk/xdr_json/`, the `stellarsdk/stellarsdkUnitTests/sep/txrep/TxRep*TestCase.swift` files, and the value tables `tools/xdr-generator/test/txrep_test_values.rb` and `tools/xdr-generator/test/json_test_values.rb`. The stellar-xdr commit is pinned as `XDR_COMMIT` in `Makefile`; the definitions in `xdr/` are tracked downloads of that commit and are never edited, `make xdr-update` re-downloads them. `make xdr-generate` regenerates from the tracked definitions and downloads only a missing one. It runs Ruby in Docker and installs the gems on every run, so with the image and the gems cached it needs no network; it takes about five minutes. The override files are the `tools/xdr-generator/generator/*_overrides.rb` files and `tools/xdr-generator/generator/txrep_types.rb`. Run `make xdr-generator-update-snapshots` only after an intended output change, and read the snapshot diff. Before an XDR update or a generator change, read `tools/xdr-generator/README.md`; it describes `SKIP_TYPES`, the override files and the setup without Docker.
- **SEP-51 conformance.** `tools/sep-51-oracle/oracle-pin.json` pins the reference CLI and the reference commits and repeats the SDK's XDR commit as `sdk_xdr_commit`. `tools/sep-51-oracle/name-map.json` and `tools/sep-51-oracle/type_map.json` are generated by `ruby tools/sep-51-oracle/name_map.rb --diff`; the corpus `stellarsdk/stellarsdkUnitTests/sep/xdr_json/corpus.json` is generated from `tools/sep-51-corpus/seeds.py` by `python3 tools/sep-51-corpus/generate_corpus.py` and lives inside the test target because SwiftPM resources cannot leave their target. The two pins move together by hand: the corpus check compares the corpus with `Makefile`, the name-map check compares `tools/sep-51-oracle/name-map.json` with the oracle pin, and no check compares the two pins with each other. `tools/sep-51-oracle/name_map.rb` loads the generator's gems (`bundle install` in `tools/xdr-generator/`); `tools/sep-51-oracle/emitted_names.rb` needs only Ruby. The pinned CLI installs with the Cargo command in the oracle README. Before moving a pin or touching XDR-JSON names, read `tools/sep-51-oracle/README.md`; it holds the modes and exit codes of the name scripts. Before adding a seed or regenerating the corpus, read `tools/sep-51-corpus/README.md`; it holds the admission rule for specification-derived seeds.
- **Compatibility matrices.** The files under `compatibility/` and `tools/matrix-generator/rpc/rpc_methods.json` describe the released SDK. Every generator run rewrites the `Generated` line, so a run that only verifies a change restores both before the commit. The matrices change in four cases. An SDK behavior change ships them with its release. A generator fix commits them in its pull request, after the maintainer has read every changed cell. A new protocol version adds its rows when it is live. A mixed diff is the maintainer's decision. The generators need network; a GitHub token in `GITHUB_TOKEN` raises the API rate limit. Before changing a generator or an analyzer, read `tools/matrix-generator/README.md`; it holds the pipelines and their inputs.
- **Agent skill.** `skills/stellar-ios-mac-sdk/references/api_reference.md` is generated by `python3 tools/skill-generator/generate_api_reference.py`. Its output on `master` includes unreleased API, so it is regenerated at release only, together with the skill version and the zip; a verification run restores the committed file. Before changing the reference generator, read `tools/skill-generator/README.md`; it holds the scan rules.
- **Test fixtures.** The six files under `stellarsdk/stellarsdkIntegrationTests/soroban/bindings/` were generated by the external contract bindings generator and are not edited. `stellarsdk/stellarsdkIntegrationTests/soroban/p28_owner_fixture.wasm` is built from `tools/p28-owner-fixture/` and replicated in four SDK repositories; before changing it, read `tools/p28-owner-fixture/README.md`; it holds the build and the replication rule. The other wasm resources are test inputs without a source in this repository. `stellarsdk/stellarsdkUnitTests/smartaccount/oz/fixtures/ed25519_cross_sdk_fixture.json` is emitted by the test gated with `REGENERATE_ED25519_FIXTURE=1` and copied to every SDK that consumes it.

## Conventions and gotchas

- The package builds in the Swift language mode `Package.swift` sets, with strict concurrency checking: data-race safety findings are compile errors, and public types are `Sendable` unless their documentation says otherwise (`OZSmartAccountAuthPayload` is a documented mutable exception).
- Unit tests mock HTTP with `ServerMock`, a `URLProtocol` registered in `setUp` and cleared with `ServerMock.removeAll()` in `tearDown`; `ResponsesMock` subclasses override `requestMock()`. When no mock matches, `canInit` returns false and the request reaches the real host, so a test with an unmatched mock depends on the network; five unit tests do.
- The service APIs (`AccountService` and its siblings) return `async` response enums with `.success` and `.failure`; `SorobanClient` and the smart-account APIs throw. Follow the convention of the API you extend, because callers of one service expect one error shape.
- Public declarations carry `///` documentation comments that describe current behavior and its reason, never history; the API documentation is generated from them.
- New code uses the typed API; raw XDR appears only where no typed path exists, because the typed layer carries the validation and the documentation users read.

## Boundaries

- Releases are the maintainer's. An agent never changes the version in `stellarsdk/stellarsdk/Info.plist`, `.jazzy.yaml`, the install snippets in `README.md`, `docs/getting-started.md` and `docs/quick-start.md`, the skill version fields in `skills/stellar-ios-mac-sdk/SKILL.md`, `skills/.claude-plugin/plugin.json` and `.claude-plugin/marketplace.json`, the zip `skills/stellar-ios-mac-sdk.zip`, a tag, a GitHub release, or the `gh-pages` branch.
- No credential lives in the repository. CI uses OIDC for the Codecov and SBOM uploads. Ask before adding a dependency, a workflow, or a new generated artifact; each is a maintenance commitment the maintainer carries after the pull request.

## Changes

- Branch from `master` with a short kebab-case name that names the change; open the pull request against `master`.
- The commit subject is one imperative sentence of at most 72 characters without a type prefix; the body states the motivation and what the change does, so the log reads without the diff. The pull request body follows the same form and names what was verified.
- A pull request carries code, tests, and the CHANGELOG entry.

## Where details live

- Before your first change, read `CONTRIBUTING.md`; it holds setup, how to report a bug or propose a feature, how a change is submitted and what the review checks.
- Before writing or changing a page under `docs/` or a documentation example, read `docs/documentation-strategy.md`; it holds the page template, the example rules (`try!` only for fixed known-good values) and the release policy for documentation.
- Before touching the skill under `skills/`, read `skills/README.md` and `tools/skill-generator/README.md`; they hold the skill's structure and the reference generator.
- Before changing a tool under `tools/`, read its README; every tool directory has one.
