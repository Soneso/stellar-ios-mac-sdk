# Migrating to 3.12.0

This guide covers the observable changes between 3.11.0 and 3.12.0. If you upgrade from an older version, also review the release notes between your version and 3.11.0 and the [3.10.0 migration guide](3.10.0.md). Each note describes one situation: whether you are affected, how it shows, and what to do.

## Fee bump submissions

- If you submit fee bump transactions through `TransactionsService.submitFeeBumpTransaction` or `submitFeeBumpAsyncTransaction`: both methods run the SEP-29 memo check against the inner transaction of the envelope they post. In 3.11.0 they posted without the check. A fee bump whose inner transaction has no memo and pays, path-pays or merges into a `G...` account flagged with `config.memo_required` returns `.destinationRequiresMemo(destinationAccountId:)` and is not posted. `TransactionPostResponseEnum` and `TransactionPostAsyncResponseEnum` carried this case in 3.11.0, so exhaustive switches compile unchanged; a `default:` arm or a `fatalError` that treated the case as unreachable for fee bumps now runs. To submit, build the inner `Transaction` again with a memo from a fresh `Account` at the original sequence number, sign it, wrap it in a new `FeeBumpTransaction`, sign the fee bump and submit again. A `FeeBumpTransaction` captures the inner envelope when it is constructed, so adding a memo to `innerTransaction` after wrapping does not change what is posted. Pass `skipMemoRequiredCheck: true` where you have verified the memo requirement yourself.
- If your fee bump submissions run against a slow or unavailable Horizon, or you count requests: unless the inner transaction has a memo or you pass `skipMemoRequiredCheck: true`, each submission issues one `GET /accounts/{id}` per distinct `G...` destination before posting and stops at the first destination that requires a memo. A 404 counts as no memo required. Any other lookup failure returns `.failure(error:)` before posting: the Horizon error, or `HorizonRequestError.parsingResponseFailed` when the account response cannot be decoded. In 3.11.0 fee bump submissions made no lookups. Handle this `.failure` like any other submission failure, or pass `skipMemoRequiredCheck: true`.
- If your HTTP-mocked fee bump tests use the default check with a memo-less inner transaction: expect up to one `GET /accounts/{id}` per distinct `G...` payment, path payment or account merge destination before the post. Register a response for each lookup the test reaches; a 404 counts as no memo required, while any other lookup error prevents the post. Tests with an inner memo, only muxed destinations, or `skipMemoRequiredCheck: true` need no account-lookup responses.
- If you store or pass either fee bump submit method as a function value: update its function type as well as any full-name reference. Both methods are now `open func ...(transaction: FeeBumpTransaction, skipMemoRequiredCheck: Bool = false)`; default arguments apply to direct calls, not to a stored function value, so `let submit = sdk.transactions.submitFeeBumpTransaction` now takes a `FeeBumpTransaction` and a `Bool`. Spell a full-name reference `submitFeeBumpTransaction(transaction:skipMemoRequiredCheck:)` or `submitFeeBumpAsyncTransaction(transaction:skipMemoRequiredCheck:)`, pass both arguments when invoking the stored function, or keep a one-argument callback with a closure that calls the method directly. If you made `TransactionsService` conform to a protocol with the 3.11.0 requirement, update the requirement and its conformers or add an adapter; declaring the protocol alone is unaffected. Direct calls with `transaction:` only compile unchanged.
- If you match the message of a fee bump encoding failure: `submitFeeBumpAsyncTransaction` returns `.failure(error: .requestFailed(message: "could not encode fee bump transaction", horizonErrorResponse: nil))`. In 3.11.0 the async message was `"could not encode transaction"`; the sync variant already used the new text. Match on the case, not the message.

## XDR decoding

- If you decode XDR from untrusted, truncated or corrupted input and match on `XDRDecoder.Error.prematureEndOfData`: also handle `StellarSDKError.xdrDecodingError(message:)`. Array counts, and the byte counts of `String` and `Data`, are checked against the remaining bytes divided by a minimum element width, 1 byte for `UInt8` (the bytes behind `String` and `Data`) and 4 bytes otherwise. A count above that bound throws `"XDR array count N exceeds the maximum of M for the R remaining bytes"` before any element is read. In 3.11.0 the guard compared the count with the raw remaining byte count and threw `prematureEndOfData` when that bound was exceeded; counts that passed went on to element decoding. Passing the new guard does not guarantee that every element and the trailing padding fit, so later reads can still throw `prematureEndOfData` or an element's own error; a handler for malformed input must catch both types. The check reaches every decode path: `init(xdr:)` on the XDR types, `Transaction(envelopeXdr:)`, `Array.init(fromBinary:)` and the readers built on it. Data that follows the XDR definitions decodes unchanged.
- If you decode hand-built or corrupted XDR whose extension point discriminant is not 0: `FeeBumpTransactionXDR`, `TransactionV0XDR`, `DataEntryXDR`, `OfferEntryXDR`, `LedgerEntryExtensionV1`, `ClaimableBalanceEntryExtensionV1` and `TrustlineEntryExtensionV2` throw `StellarSDKError.xdrDecodingError(message: "<Type> extension point must be 0, got N")`. In 3.11.0 the five generated types decoded the value and re-encoded 0, and `FeeBumpTransactionXDR` and `TransactionV0XDR` stored and re-encoded the value. Data from the network carries 0. Fix the producer of the non-zero value.
- If you decode XDR that carries a key type other than ed25519 in an `AccountID` or a muxed account: `PublicKey` throws `StellarSDKError.xdrDecodingError(message: "Unknown PublicKey discriminant: N")` for any type other than `PUBLIC_KEY_TYPE_ED25519`, and `MuxedAccountXDR` throws `"Unknown MuxedAccountXDR discriminant: N"` for any type other than `KEY_TYPE_ED25519` and `KEY_TYPE_MUXED_ED25519`. In 3.11.0 both read the 32 bytes after the discriminant as an ed25519 key. The check reaches every type with an account field, among them transaction and fee bump source accounts, payment and account merge destinations, and every `Transaction(envelopeXdr:)` decode. The XDR definitions allow no other arms, so data from the network decodes unchanged.
- If you call `Data(fromBinary:count:)` or `Array(fromBinary:count:)` on an `XDRDecoder`: both read the XDR fixed-length layout. `Data(fromBinary:count:)` reads exactly `count` raw bytes with no length prefix and no padding, the layout `Data.xdrEncodeFixed(to:)` writes. `[T](fromBinary:count:)` reads exactly `count` elements with no count prefix. In 3.11.0 `Data(fromBinary:count:)` delegated to `Array(fromBinary:count:)`, which resolved to the `XDRDecodable` protocol default: it ignored `count`, read a 4-byte length prefix and then that many elements, and consumed no padding. A negative `count` throws `StellarSDKError.xdrDecodingError(message: "XDR array count N is negative")`. A `count` above the remaining-input bound described above throws the remaining-bytes message; wider or variable-width array elements can still exhaust the input during element decoding and throw `XDRDecoder.Error.prematureEndOfData`. The declaration on `Array` is new; the call compiled in 3.11.0 through the protocol default. For a length-prefixed field, position the decoder at the prefix and use `Data(fromBinary:)` or `Array(fromBinary:)`; `Data(fromBinary:)` also consumes the field's padding, so remove any separate padding read for that field. For fixed-width bytes, keep `Data(fromBinary:count:)` and position the decoder at the first payload byte; remove any synthetic prefix you inserted to work around the 3.11.0 behavior. If you decode a real wire-format length prefix yourself and pass its value as `count`, keep that prefix read and handle any required padding yourself. No SDK type calls these initializers, so the SDK's own decoding is unaffected.

## Strkey and hex helpers

- If you call `Data.encodeMuxedAccount()` on bytes the SDK did not produce: the key type in the first 4 bytes is read first and decides the width. An unknown key type throws `StellarSDKError.invalidArgument(message: "invalid muxed account key type K, must be KEY_TYPE_ED25519 or KEY_TYPE_MUXED_ED25519")` at any width of at least 4 bytes. In 3.11.0, 36-byte input with an unknown key type encoded to the `G...` strkey of its 32 key bytes. A wrong width reports the width the key type requires: `"invalid ed25519 muxed account length N, must be 36 bytes"` or `"invalid med25519 muxed account length N, must be 44 bytes"`. In 3.11.0 input shorter than its key type's width got the generic `"invalid muxed account length N, must be 36 bytes (44 for KEY_TYPE_MUXED_ED25519)"`, which 3.12.0 reports only for fewer than 4 bytes. Well-formed 36-byte ed25519 and 44-byte muxed input encodes the same strkeys as before. If the key type throw fires, fix the producer of the bytes.
- If you match the message of `String.encodeContractIdHex()`, `encodeClaimableBalanceIdHex()` or `encodeLiquidityPoolIdHex()` for non-hex input: the messages read `"invalid contract id, not a hex string <input>"`, `"invalid claimable balance id, not a hex string <input>"` and `"invalid liquidity pool id, not a hex string <input>"`. In 3.11.0 all three read `"Not a hex string <input>"`. The error type is unchanged, `StellarSDKError.invalidArgument`, and wrong-width hex input keeps its messages.

## Smart accounts

- If you catch `SmartAccountTransactionException.SigningFailed` around `SmartAccountUtils.deriveContractAddress(credentialId:deployerPublicKey:networkPassphrase:)`: the method no longer throws it. Every failure in the derivation throws `SmartAccountValidationException.InvalidInput` with the message `"Invalid input for contractId: Failed to derive contract ID: <error>"`, where `<error>` is the underlying error's `localizedDescription`. In 3.11.0 a preimage encoding failure threw `SigningFailed`, and a strkey encoding failure threw `InvalidInput` with the message `"Invalid input for contractId: Failed to encode contract ID: <error>"`. An invalid deployer key still throws `SmartAccountValidationException.InvalidAddress`. The derived address is unchanged for every input. These exceptions are classes, so a catch dedicated to this call reads `catch is SmartAccountValidationException.InvalidInput`; remove the `SigningFailed` clause for this call.
