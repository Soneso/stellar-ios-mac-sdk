# Migrating to 3.10.0

This guide covers the observable changes between 3.9.0 and 3.10.0. If you upgrade from an older version, also review the release notes between your version and 3.9.0. Each note describes one situation: whether you are affected, how it shows, and what to do.

- If you simulate Soroban transactions or read auth entries from simulation: `SimulateTransactionRequest` and `MethodOptions` now default `useUpgradedAuth` to true and always send the flag, so simulation against a Protocol 27+ RPC returns entries carrying `ADDRESS_V2` credentials. The arm-specific accessor `SorobanCredentialsXDR.address` is nil on them, so `if let` / `guard let` paths over simulation entries take the else branch and skip them, and a force-unwrap (`address!`) traps; read either arm through `addressCredentials`. On a network below Protocol 27, pass `useUpgradedAuth: false`. `ADDRESS_V2` entries invalidate the transaction there.
- OpenZeppelin smart accounts: if your relayer rejects submissions after the upgrade (it cannot parse Protocol 27 authorization XDR), set `useUpgradedAuth: false` in `OZSmartAccountConfig`. If an external wallet cannot sign the address-bound preimage type, set `useUpgradedAuthForWalletSigners: false`. Each flag controls only its own path. Direct callers of `OZSmartAccountAuth.buildSourceAccountAuthPayloadHash` get a compile error: pass the address the credentials will carry as the new second argument, and `useUpgradedAuth: false` when building legacy credentials, so the hash matches the credential arm.
- If you use the CAP-85 executable-tag types from 3.8.1/3.9.0: the tag is raw bytes in 3.10.0. Code reading `ContractExecutableExternalRefXDR.tag` as a `String`, or pattern-matching `SCValXDR.executableTag(let s)` into a `String`, gets a compile error: the payload is `Data`. Read text tags through `tagString` / `executableTagString` (nil when the bytes spell no text). Building from text keeps compiling: the `init(executableOwner:tag: String)` initializer and the `SCValXDR.executableTag(_ string:)` factory encode UTF-8 once. The helper accessor `SCValXDR.executableTag: String?` is deprecated: use `executableTagString`. The deprecated accessor returns nil for a binary tag. In 3.9.0 it returned the stored string unconditionally.
- If you build keypairs or keys from user input or storage: `PublicKey(accountId:)`, `KeyPair(accountId:)`, `Seed(secret:)`, and `KeyPair(secretSeed:)` reject corrupted or wrong-width strkeys. A mistyped account id or seed throws `Ed25519Error.invalidPublicKey` / `invalidSeed` at construction. Every malformed secret throws `invalidSeed`, so `invalidSeedLength` handlers on the string path do not fire. In 3.9.0 such strkeys decoded silently, and a wrong-length secret threw `Ed25519Error.invalidSeedLength`.
- If you encode strkeys from raw bytes: every `Data.encode*` method (`encodeEd25519PublicKey`, `encodeContractId`, `encodeLiquidityPoolId`, and the rest) throws `StellarSDKError.invalidArgument` for input of a width it does not admit. The same applies to `Signer.signedPayload`, which also rejects an empty payload. In 3.9.0 wrong-width input encoded a strkey for a value you never passed or, for `encodeMuxedAccount`, surfaced a decoder error or silently ignored trailing bytes, and `Signer.signedPayload` accepted an empty payload. Nothing to change if your byte widths are correct. If the throw fires, fix the source of the wrong-width bytes rather than catching and continuing.
- If you call `TrustlineAssetXDR(poolId:)` or `LedgerKeyContractCodeXDR(wasmId:)`: both are throwing initializers, so the call does not compile until you add `try`. They reject anything but a 64-character hex id. In 3.9.0 they did not throw, and any other input built a key over bytes the caller never named.
- If you call `String.wrappedData32FromHex()`: it is now `wrappedData32FromHex(idKind:) throws` (compile error). Pass a short label naming the id kind. It appears in the error message.
- If you read `AssetBalanceChange.to`: it is `String?` (compile error until you unwrap). Horizon omits `to` on burn and clawback balance changes, and those operations parse. In 3.9.0 `to` was a `String`, and those operations failed the whole response decode.
- If you call `LedgerEntryDataXDR.isBool`: it is removed (compile error). `LedgerEntryData` has no bool arm. In 3.9.0 the property compared the ledger entry type number against an unrelated enum and answered true for every account entry, so it never carried meaning. Delete the call.
- If you store or compare claimable balance ids: ids read back from parsed XDR are spelled longer in 3.10.0. `ClaimClaimableBalanceOperation.balanceId`, `ClawbackClaimableBalanceOperation.claimableBalanceID`, and `SCAddressXDR.claimableBalanceId` report the 72-character hex form Horizon serves, so comparisons against ids stored before 3.10.0 fail on the spelling. In 3.9.0 they reported 64 or 66 characters. Convert either side with `ClaimableBalanceIDXDR(claimableBalanceId: stored).paddedBalanceIdHex`, which accepts every spelling, or store the new form. Everything you pass into the SDK keeps working: the balance-id APIs accept the strkey and all three hex widths.
- If your app stored a `B...` string that is 63 characters long instead of the correct 58: those strings are not valid SEP-23 strkeys, and no 3.10.0 API reads or decodes them. In 3.9.0 they decoded, and only `encodeClaimableBalanceId` built them, from the id's 36-byte XDR encoding. Re-fetch the balance's id from Horizon (for example through `sdk.claimableBalances.getClaimableBalances(claimantAccountId:...)`) and store what Horizon returns.
- If you query claimable balances by id: the service and stream methods validate the id up front and fail with `HorizonRequestError.badRequest`, naming the rule, before any request goes out. The claimable-balance transactions stream delivers its events. In 3.9.0 a malformed id, or even a valid `B...` strkey, was sent in a form Horizon rejects, and the stream targeted a route Horizon does not serve, so it never delivered an event.
- If you pass contract or liquidity pool ids as hex: `SCAddressXDR(contractId:)`, `SCAddressXDR(liquidityPoolId:)`, the liquidity-pool operation XDR helpers, and the contract-creation builders require exactly 64 hex characters and throw `StellarSDKError.invalidArgument`. In 3.9.0 the contract-creation builders zero-padded odd input, stripped leading zero pairs, and read non-hex characters as zero, building an id you never passed. In 3.9.0 the address and liquidity-pool factories threw `StellarSDKError.encodingError` for non-hex input and silently accepted even-width hex of the wrong length. Change handlers matching `encodingError` to match `invalidArgument`. A 64-character hex contract id that begins with an uppercase `C` parses; in 3.9.0 it was misread as a strkey and rejected, and lowercase hex was never affected.
- If you convert hex ids to strkeys with `encodeContractIdHex()`, `encodeLiquidityPoolIdHex()`, or `encodeClaimableBalanceIdHex()`: a value of the wrong width, or a claimable-balance id with a wrong discriminant, throws `StellarSDKError.invalidArgument`. In 3.9.0 such a value encoded a strkey over bytes you never passed. Contract and pool ids must spell exactly 32 bytes; a claimable-balance id may be the 64, 66, or 72-character form with a V0 discriminant. Nothing to change if your inputs are well-formed; otherwise validate the id where it enters your app or handle the throw at the call.
- If you parse handcrafted or persisted TxRep (SEP-11): a line that spells a fixed-width value with too few or too many hex digits throws `TxRepError.invalidValue` naming the key. The fixed-width values are hashes, signer keys, signature hints, salts, asset codes, and pool, contract, and balance ids. In 3.9.0 such a line decoded to a value of the spelled width and re-encoded to malformed XDR. Emit the exact declared widths. The same strictness reaches SEP-51 XDR-JSON reads: a document carrying a zero-length signed payload or an unknown claimable-balance discriminant fails with `XdrJsonError.invalidValue`.
- If you match on Soroban contract-loading error messages: the shared "could not extract wasm id" message is split into per-condition messages (missing instance entry, non-instance entry, Stellar Asset Contract). String matchers on the old text do not match; match on the failure case, not the message.
