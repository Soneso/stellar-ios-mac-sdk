# Migrating to 3.10.0

This guide covers the observable changes between 3.9.0 and 3.10.0. If you upgrade from an older version, also review the release notes between your version and 3.9.0. Each note describes one situation: whether you are affected, how it shows, and what to do.

- If you simulate Soroban transactions or read auth entries from simulation: `SimulateTransactionRequest` and `MethodOptions` now default `useUpgradedAuth` to true and always send the flag, so simulation against a Protocol 27+ RPC returns entries carrying `ADDRESS_V2` credentials. The arm-specific accessor `SorobanCredentialsXDR.address` is nil on them, so `if let` / `guard let` paths over simulation entries take the else branch and skip them, and a force-unwrap (`address!`) traps; read either arm through `addressCredentials`. On a network below Protocol 27, pass `useUpgradedAuth: false` — `ADDRESS_V2` entries invalidate the transaction there.
- OpenZeppelin smart accounts: if your relayer rejects submissions after the upgrade (it cannot parse Protocol 27 authorization XDR), set `useUpgradedAuth: false` in `OZSmartAccountConfig`; if an external wallet can no longer sign (it cannot sign the address-bound preimage type), set `useUpgradedAuthForWalletSigners: false`. Each flag controls only its own path. Direct callers of `OZSmartAccountAuth.buildSourceAccountAuthPayloadHash` get a compile error: pass the address the credentials will carry as the new second argument, and `useUpgradedAuth: false` when building legacy credentials, so the hash matches the credential arm.
- If you use the CAP-85 executable-tag types from 3.8.1/3.9.0: the tag is raw bytes now. Code reading `ContractExecutableExternalRefXDR.tag` as a `String`, or pattern-matching `SCValXDR.executableTag(let s)` into a `String`, gets a compile error — the payload is `Data`. Read text tags through `tagString` / `executableTagString` (nil when the bytes spell no text). Building from text keeps compiling: the `init(executableOwner:tag: String)` initializer and the `SCValXDR.executableTag(_ string:)` factory encode UTF-8 once. The helper accessor `SCValXDR.executableTag: String?` is deprecated — use `executableTagString`; note it now returns nil for a binary tag, where it previously returned the stored string unconditionally.
- If you build keypairs or keys from user input or storage: `PublicKey(accountId:)`, `KeyPair(accountId:)`, `Seed(secret:)`, and `KeyPair(secretSeed:)` now reject corrupted or wrong-width strkeys that previously decoded silently — a mistyped account id or seed throws `Ed25519Error.invalidPublicKey` / `invalidSeed` at construction. One error-type change: a wrong-length secret previously threw `Ed25519Error.invalidSeedLength`; every malformed secret now throws `invalidSeed`, so `invalidSeedLength` handlers on the string path no longer fire.
- If you encode strkeys from raw bytes: every `Data.encode*` method (`encodeEd25519PublicKey`, `encodeContractId`, `encodeLiquidityPoolId`, and the rest) throws `StellarSDKError.invalidArgument` for input of a width it does not admit; wrong-width input previously encoded a strkey or, for `encodeMuxedAccount`, surfaced a decoder error or silently ignored trailing bytes. The same applies to `Signer.signedPayload`, which now also rejects an empty payload. Nothing to change if your byte widths are correct. If the throw fires, the same call previously produced a strkey for a value you never passed — fix the source of the wrong-width bytes rather than catching and continuing.
- If you call `TrustlineAssetXDR(poolId:)` or `LedgerKeyContractCodeXDR(wasmId:)`: both are now throwing initializers — add `try` (compile error until you do). They reject anything but a 64-character hex id, which previously built a key over bytes the caller never named.
- If you call `String.wrappedData32FromHex()`: it is now `wrappedData32FromHex(idKind:) throws` (compile error). Pass a short label naming the id kind — it appears in the error message.
- If you read `AssetBalanceChange.to`: it is `String?` now (compile error until you unwrap). Horizon omits `to` on burn and clawback balance changes; those operations previously failed the whole response decode and now parse.
- If you call `LedgerEntryDataXDR.isBool`: it is removed (compile error). `LedgerEntryData` has no bool arm; the property compared the ledger entry type number against an unrelated enum and answered true for every account entry, so it never carried meaning. Delete the call.
- If you store or compare claimable balance ids: ids read back from parsed XDR are spelled longer now. `ClaimClaimableBalanceOperation.balanceId`, `ClawbackClaimableBalanceOperation.claimableBalanceID`, and `SCAddressXDR.claimableBalanceId` report the 72-character hex form Horizon serves (previously 64 or 66 characters), so comparisons against ids stored before 3.10.0 fail on the spelling. Convert either side with `ClaimableBalanceIDXDR(claimableBalanceId: stored).paddedBalanceIdHex` — it accepts every spelling — or store the new form. Everything you pass into the SDK keeps working: the balance-id APIs accept the strkey and all three hex widths.
- If your app stored a `B...` string that is 63 characters long instead of the correct 58 — possible only if it was built by 3.9.0's `encodeClaimableBalanceId` from the id's 36-byte XDR encoding — those strings are not valid SEP-23 strkeys, no 3.10.0 API reads them, and they no longer decode. Re-fetch the balance's id from Horizon (for example through `sdk.claimableBalances.getClaimableBalances(claimantAccountId:...)`) and store what Horizon returns.
- If you query claimable balances by id: the service and stream methods now validate the id up front and fail with `HorizonRequestError.badRequest`, naming the rule, before any request goes out — previously a malformed id, or even a valid `B...` strkey, was sent in a form Horizon rejects. The claimable-balance transactions stream previously targeted a route Horizon does not serve and never delivered an event; it now works.
- If you pass contract or liquidity pool ids as hex: `SCAddressXDR(contractId:)`, `SCAddressXDR(liquidityPoolId:)`, the liquidity-pool operation XDR helpers, and the contract-creation builders require exactly 64 hex characters and throw `StellarSDKError.invalidArgument`. Previously the contract-creation builders zero-padded odd input, stripped leading zero pairs, and read non-hex characters as zero — building an id you never passed — while the address and liquidity-pool factories threw `StellarSDKError.encodingError` for non-hex input and silently accepted even-width hex of the wrong length. Handlers matching `encodingError` must match `invalidArgument` now. And a 64-character hex contract id that begins with an uppercase `C` now parses — it was previously misread as a strkey and rejected (lowercase hex was never affected).
- If you convert hex ids to strkeys with `encodeContractIdHex()`, `encodeLiquidityPoolIdHex()`, or `encodeClaimableBalanceIdHex()`: a value of the wrong width — or, for a claimable balance, with a wrong discriminant — now throws `StellarSDKError.invalidArgument`, where it previously encoded a strkey over bytes you never passed. Contract and pool ids must spell exactly 32 bytes; a claimable-balance id may be the 64, 66, or 72-character form with a V0 discriminant. Nothing to change if your inputs are well-formed; otherwise validate the id where it enters your app or handle the throw at the call.
- If you parse handcrafted or persisted TxRep (SEP-11): a line spelling a fixed-width value — a hash, signer key, signature hint, salt, asset code, or pool/contract/balance id — with too few or too many hex digits now throws `TxRepError.invalidValue` naming the key. Such a line previously decoded to a value of the spelled width and re-encoded to malformed XDR. Emit the exact declared widths. The same strictness reaches SEP-51 XDR-JSON reads: a document carrying a zero-length signed payload or an unknown claimable-balance discriminant now fails with `XdrJsonError.invalidValue`.
- If you match on Soroban contract-loading error messages: the shared "could not extract wasm id" message is split into per-condition messages (missing instance entry, non-instance entry, Stellar Asset Contract). String matchers on the old text no longer fire; match on the failure case, not the message.
