# Migrating to 3.13.0

This guide covers the observable changes between 3.12.0 and 3.13.0. If you upgrade from an older version, also review the [GitHub release notes](https://github.com/Soneso/stellar-ios-mac-sdk/releases) of the versions between yours and 3.12.0 and the earlier migration guides, newest first: [3.12.0](3.12.0.md), [3.10.0](3.10.0.md). Each note describes one situation: whether you are affected, how it shows, and what to do.

## XDR-JSON asset codes

- If you read XDR-JSON with `fromXdrJson(_:)` of `AssetXDR`, `ChangeTrustAssetXDR`, `TrustlineAssetXDR` or a type that contains one, or with `AssetCode12XDRJsonCodec`: a `credit_alphanum12` code that unescapes to fewer than 5 bytes throws `XdrJsonError.invalidValue`, with the message `"expected 5 to 12 bytes, got 3"` for `"ABC"`. A code longer than 12 bytes reports `"expected 5 to 12 bytes, got 13"` for 13 bytes. In 3.12.0 a short code decoded without an error, and a 13-byte code read `"expected at most 12 bytes, got 13"`. Pad a short code with escaped NUL bytes to 5 bytes, `"ABC\\0\\0"` in the JSON text, and match on the case rather than the message. XDR-JSON the SDK wrote pads this way and reads back unchanged.

## Contract arguments

- If you pass an `M...` strkey for an `Address` parameter to `ContractSpec.nativeToXdrSCVal(val:ty:)` or `funcArgsToXdrSCValues(name:args:)`: the call throws `ContractSpecError.invalidType(message: "Address takes an account (G...) or contract (C...) address, got the muxed address <address>, which needs a MuxedAddress parameter")`. In 3.12.0 the strkey was encoded as a muxed account address. Pass the account behind it, or call a contract function whose parameter is a `MuxedAddress`:

  ```swift
  // 3.12.0
  let arg = try spec.nativeToXdrSCVal(val: muxedId, ty: .address)
  ```

  ```swift
  // 3.13.0
  let arg = try spec.nativeToXdrSCVal(val: try MuxedAccount(accountId: muxedId).ed25519AccountId, ty: .address)
  ```

- If you pass a contract id as 64 hexadecimal characters for an `Address` parameter: the call throws `ContractSpecError.invalidType(message: "Invalid address format: <hex>; Address takes an account (G...) or contract (C...) address")`. In 3.12.0 a hex id beginning with uppercase `C`, regardless of the remaining letters' case, was encoded as that contract, and every other hex id threw `StellarSDKError.encodingError`. Convert the id to its `C...` strkey first:

  ```swift
  // 3.12.0
  let arg = try spec.nativeToXdrSCVal(val: contractIdHex, ty: .address)
  ```

  ```swift
  // 3.13.0
  let arg = try spec.nativeToXdrSCVal(val: try contractIdHex.encodeContractIdHex(), ty: .address)
  ```

- If you catch the errors of `nativeToXdrSCVal(val:ty:)` or `funcArgsToXdrSCValues(name:args:)` for rejected addresses: every rejected value for an `Address` or `MuxedAddress` parameter throws `ContractSpecError.invalidType`, whose message names the parameter type and the value or its type. In 3.12.0 a string for an `Address` parameter that started with neither `G`, `M` nor `C`, among them `B...` and `L...` strkeys, threw `StellarSDKError.encodingError`. A malformed `G...` strkey threw `Ed25519Error.invalidPublicKey`, a malformed `M...` or 56-character `C...` strkey a `KeyUtilsError`, and any other `C...` string that was no hex id `StellarSDKError.invalidArgument`. Catch `ContractSpecError.invalidType(let message)` for all of them.
- If you prebuilt an `SCValXDR.address(...)` for an `Address` or `MuxedAddress` parameter because the conversion rejected your value: `nativeToXdrSCVal(val:ty:)` takes an account or contract `SCAddressXDR` for both parameter types. A `MuxedAddress` parameter also takes `G...`, `M...`, `C...` and `W...` strkeys and the matching `SCAddressXDR` values. In 3.12.0 an `SCAddressXDR` value threw `ContractSpecError.conversionFailed`, and every string for a `MuxedAddress` parameter threw `ContractSpecError.invalidType`. A prebuilt `SCValXDR` passes through without a check, so your code keeps working. To have the address checked, pass the strkey or the `SCAddressXDR` value:

  ```swift
  // 3.12.0
  let arg = try spec.nativeToXdrSCVal(val: SCValXDR.address(try SCAddressXDR(accountId: muxedId)), ty: .muxedAddress)
  ```

  ```swift
  // 3.13.0
  let arg = try spec.nativeToXdrSCVal(val: muxedId, ty: .muxedAddress)
  ```

- If you pass a Swift dictionary for a `map` parameter or for a struct with named fields: the entries are sorted into the key order the Soroban host requires. Keys that convert to the same value throw `StellarSDKError.invalidArgument(message: "Duplicate ScMap key: <key>")`, with the key in XDR-JSON. In 3.12.0 map entries kept the dictionary's iteration order, which varies between runs of the app, and struct fields kept the order of the contract specification. In 3.12.0 duplicate keys were encoded twice. Give each key once. To build a map value yourself, use `SCValXDR.sortedMap(_:)`, which sorts and rejects duplicates the same way.

## XDR types

- If you `switch` exhaustively over `SCAddressType`, `SCAddressXDR` or `ContractCostType`: the switch does not compile until it handles `SCAddressType.muxedContract` (value 5), `SCAddressXDR.muxedContract`, which carries a `MuxedContractXDR`, and the nine `ContractCostType` cases from `mlDsa44DecodeVerifyingKey` (86) through `verifyMlDsa87Sig` (94). In 3.12.0 decoding address type 5 threw `StellarSDKError.xdrDecodingError(message: "Unknown SCAddressXDR discriminant: 5")`, and decoding a cost type from 86 to 94 threw `DecodingError.dataCorrupted`. Add the cases, or a `default:` arm where they need no handling.
- If you `switch` exhaustively over `StellarValueTypeXDR` or `StellarValueXDRExtXDR`: add `StellarValueTypeXDR.signedMs` (3) and `emptyTxSetMs` (4), and `StellarValueXDRExtXDR.signedMsValue` and `proposedMsValue`, whose payloads carry `closeTimeMs` as `UInt64`. In 3.12.0 decoding value type 3 or 4 threw `DecodingError.dataCorrupted`, and the two extension arms threw `StellarSDKError.xdrDecodingError(message: "Unknown StellarValueXDRExtXDR discriminant: N")`. Existing values decode unchanged.

## Soroban authorization

- If you sign an authorization entry whose credential address is a muxed account (`M...`) or muxed contract (`W...`) address, with `SorobanAuthorizationEntryXDR.sign`, `withDelegates`, `AssembledTransaction.signAuthEntries` or `WebAuthForContracts.signAuthorizationEntries`: the call throws `StellarSDKError.invalidArgument(message: "Muxed account (M...) and muxed contract (W...) addresses are not valid Soroban auth credential addresses: <address>; use the underlying G... or C... address instead")`. `signAuthEntries` and `signAuthorizationEntries` check every entry, including the entries of other signers, before they stamp or sign any. In 3.12.0, for a muxed account (`M...`) credential, `sign` signed the entry, `withDelegates` built one, and `signAuthEntries` and `signAuthorizationEntries` left an unmatched entry unsigned. Pass the underlying `G...` or `C...` address to the contract call that produces the entry.
- If you pass a muxed `forAddress` to `SorobanAuthorizationEntryXDR.sign` or a muxed delegate address to `withDelegates`: the `StellarSDKError.invalidArgument` message reads `"Muxed account (M...) and muxed contract (W...) addresses are not valid Soroban auth addresses: <address>"`. In 3.12.0 it read `"Unsupported strkey prefix for delegate address: <address>"`. Pass the `G...` or `C...` address, and match on the case rather than the message.
- If a second signer calls `AssembledTransaction.signAuthEntries` without `validUntilLedgerSeq` on an entry that already carries a signature, at the top level or in a delegate node: the entry keeps its stored `signatureExpirationLedger`. The call fetches no latest ledger for it. In 3.12.0 every call stamped the latest ledger plus 100 into each matching entry. When the computed expiration differed from the stored value, the earlier signatures did not cover the new value, and the host rejected the entry. Your code needs no change, and an explicit stored value is accepted too.
- If you pass an explicit expiration, `validUntilLedgerSeq` to `signAuthEntries` or `signatureExpirationLedger` to `SorobanAuthorizationEntryXDR.sign`, for an entry that already carries a signature: a value other than the stored one throws `StellarSDKError.invalidArgument(message: "The authorization entry already carries a signature committed to signatureExpirationLedger 1100; the requested expiration 1200 would invalidate it. Pass 1100 or omit the expiration.")`. In 3.12.0 both functions stamped the new value, which invalidated the earlier signatures; an omitted value kept the stored one in `sign` in both versions. For every signer after the first, omit the value or pass the stored one:

  ```swift
  // 3.12.0
  try await tx.signAuthEntries(signerKeyPair: cosigner, validUntilLedgerSeq: latestLedger + 100)
  ```

  ```swift
  // 3.13.0
  try await tx.signAuthEntries(signerKeyPair: cosigner)
  ```

- If you call `AssembledTransaction.sign` or `signAndSend` for a transaction with a `SOROBAN_CREDENTIALS_ADDRESS_WITH_DELEGATES` entry whose top-level account (`G...`) signature is void and whose nonempty delegate tree has a signature at every node: `sign` throws `AssembledTransactionError.multipleSignersRequired`. `needsNonInvokerSigningBy()` names the account. In 3.12.0 `sign` treated the account as covered by its delegates, passed its other unsigned entries as well, and the host rejected the envelope, because an account authenticates with its own signatures. Have the account sign its entries, for example with `signAuthEntries(signerKeyPair:)`, before you call `sign`.
- If you call `AssembledTransaction.sign` while only contract addresses (`C...`) are unsigned: `sign` completes, because a contract's `__check_auth` decides which signatures it needs. In 3.12.0 `sign` threw `AssembledTransactionError.multipleSignersRequired` for them: `needsNonInvokerSigningBy()` reports a contract as its 64-character hex id, and the check skipped only addresses that start with `C`. A workaround that bypassed `sign` for such transactions can go.
- If an authorization entry carries an empty vector (`SCValXDR.vec([])`) as its signature: the entry counts as unsigned. `needsNonInvokerSigningBy()` reports its address, and `AssembledTransaction.sign` throws `AssembledTransactionError.multipleSignersRequired` when the address is an account, never for a contract. In 3.12.0 an empty vector counted as a signature, and `sign` passed. Sign the entry, for example with `signAuthEntries(signerKeyPair:)`; `SorobanAuthorizationEntryXDR.carriesSignature(_:)` tells whether a signature value counts.

## Smart accounts

- If you pass a muxed account (`M...`) or muxed contract (`W...`) address to `OZExternalSignerManager.signAuthEntry` or `OZSmartAccountAuth.buildSourceAccountAuthPayloadHash`, or an entry with such a credential address to `OZSmartAccountAuth.buildAuthPayloadHash`: the call throws `SmartAccountTransactionException.SigningFailed`. Its message names the address. A muxed wallet address in the `selectedSigners` of `OZMultiSignerManager` throws `SmartAccountValidationException.InvalidInput` with the same refusal before the availability check. In 3.12.0, for a muxed account (`M...`) address, the two payload builders returned a hash. `signAuthEntry` threw `SmartAccountSignerException.NotFound`, and a muxed `selectedSigners` address failed the availability check with `InvalidInput`, unless a wallet adapter claimed the address. Pass the underlying `G...` or `C...` address; a dedicated catch reads `catch is SmartAccountTransactionException.SigningFailed`.

## Liquidity pool assets

- If you build a pool share with `ChangeTrustAsset(assetA:assetB:)` or read one with `ChangeTrustAsset.fromXDR(assetXDR:)` from two credit assets of the same type and code: the issuers sort by their raw 32-byte public keys, the order stellar-core requires. Strkey text sorts some pairs the other way, so a pair that 3.12.0 accepted can throw and one it rejected can pass. For two `USDC` assets issued by `GD2VSLB7BPYNKQIF2P632VIVMVXPMU2B5RJU2WO4GATAJRSIDC24ZDUO` (first key byte `0xF5`) and `GDHXVH2CWS5EZLHKSHQXPLVWVJUNNXGLA2RBQQFS3LMMQIXD437QEIRQ` (`0xCF`), the `GDHX...` asset goes first. In 3.12.0 the strkey text put the `GD2V...` asset first. Swap the pair where the call throws:

  ```swift
  // 3.12.0
  let poolShare = try ChangeTrustAsset(assetA: usdcGD2V, assetB: usdcGDHX)
  ```

  ```swift
  // 3.13.0
  let poolShare = try ChangeTrustAsset(assetA: usdcGDHX, assetB: usdcGD2V)
  ```

- If you match the message of a reversed pair from `ChangeTrustAsset(assetA:assetB:)` or `fromXDR(assetXDR:)`: the `StellarSDKError.invalidArgument` message names both assets in canonical form, `"Assets are in wrong order: <assetA> sorts after <assetB>. Sort by: Native < AlphaNum4 < AlphaNum12, then by code bytes, then by issuer public key bytes."` In 3.12.0 every reversed pair read `"Assets are in wrong order. Sort by: Native < AlphaNum4 < AlphaNum12, then by Code, then by Issuer, using lexicographic ordering."` Match on the case rather than the message.

## Soroban RPC responses

- If you need the diagnostic events that `SorobanServer.getTransaction(transactionHash:)` returns: `GetTransactionResponse.diagnosticEventsXdr` holds the list that stellar-rpc returns at the top level of the response. In 3.12.0 the response did not decode that list, and `events?.diagnosticEventsXdr` was `nil` for it. Read `GetTransactionResponse.diagnosticEventsXdr`. `TransactionEvents.diagnosticEventsXdr` is deprecated, compiles with a warning, and decodes only the nested field of older response data.
